# 0035 - Customer-owned history and identity erasure

- Context: the original brief requires customer history and `flow.forget_customer`, restricted to the authenticated customer.
- Decision: expose history in Ordering at `GET /api/kiosks/{kioskId}/customer/history?page=1`; add the source flow endpoint in Identity at `POST /api/kiosks/{kioskId}/flows/forget_customer` with an empty JSON object.
- Both require the Customer policy and a kiosk claim matching the route. Customer ID comes exclusively from signed `sub`; a caller cannot supply a target customer. Extra body fields are rejected.
- History projects only the authenticated customer's orders, newest first with stable ID ordering, 25 per page plus hasMore. It includes status, totals, earned/redeemed points, item names and shop name, matching the source view's intent.
- Ordering reads its own tables; Identity-owned helpers supply current loyalty points and merchant names. These reads share a repeatable-read transaction. Tracking capabilities, e-card content, bank details, phone/email and other customers are not exposed.
- Kiosk API responses are no-store, including authentication and authorization failures. The existing API token validator checks the current user status on every authenticated request.
- Erasure calls the original SQL unchanged: phone is cleared, email replaced by a synthetic deleted address, name anonymized, account disabled and points zeroed. Existing sessions then fail authentication. An audit identifies the affected customer.
- Erasure retains the user ID and historical order/payment/audit records. It does not claim to delete every record or any pending refund destination; those bank fields follow the existing post-refund cleanup flow. UI wording must state these limits before confirmation.
- Tests create only isolated synthetic customers and verify ownership, kiosk/role restrictions, pagination, redaction, forged target rejection, source anonymization, retained orders, audit and rejection of the old token. No real customer erasure was performed.
- Kiosk UI opens a dedicated account screen before checkout, keeping purchase controls out of the erasure flow. It uses component state, requires review plus a checkbox before the explicit POST, and ends the session after success or an uncertain write outcome. Reads are explicit and paginated; no mutation retries occur.
- Closing the account screen drops history. Tab hiding ends the private session; unmount invalidates late responses. The existing absolute ten-minute and inactivity expiry remain active. Completing erasure clears customer state and query caches while retaining only a generic result notice.
- Browser tests cover focus, mobile/desktop axe, pagination, cancel/confirm, offline/read errors, expired sessions, response loss and late responses. Real browser/gateway/API/Valkey/PostgreSQL integration passes OTP issuance/verification, history, erasure, audit, retained order and old-token rejection. OTP delivery uses Development-only code in the disposable test stack; external SMS delivery remains unverified.
